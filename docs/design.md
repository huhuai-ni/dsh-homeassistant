# 设计与取舍

这份文档解释**为什么这么做**，而不是怎么用。想看用法请回 [README](../README.md)。

---

## 一、要解决的问题

> 让 AI 助手能控制家里的灯。

听起来一句话，实际上要回答三个问题：

1. **走谁的协议？**（小米的、HA 的、还是模拟人点屏幕）
2. **凭证从哪来？**（token、账号密码、还是不用凭证）
3. **谁承担维护成本？**（插件作者、还是上游社区）

---

## 二、四条路，逐一否掉

### 方案 A：miIO 局域网直连

**做法**：拿每个设备的 `token` + IP，直接发 UDP 加密包。

**优点**：最快、不依赖云、断网也能用。

**死因**：token 只能从「小米云登录」里拿。而第三方库 `micloud` 的登录流程已经被小米改掉，
实测报 `MiCloudAccessDenied`。也就是说，**门槛卡在第一步，后面再优雅也没用**。

### 方案 B：小米云 API 直连

**做法**：登录小米账号 → 从云端拉设备列表 → 调云端接口开关。

**优点**：不用 token。

**死因**：同 A，登录接口对不上；另外官方 MIoT 开放平台只对企业开放。

### 方案 C：模拟点击（adb / Appium）

**做法**：用 adb 截图，算出按钮坐标，`input tap` 点下去。

**优点**：零协议依赖，什么 App 都能点。

**死因**：

- 平板得亮屏、解锁、米家在前台
- 界面一改版，坐标全错
- 一次操作 = 截图 + 计算 + 点击 + 再截图，慢且脆

> 实测确实能用（本项目作者用它开关过灯），但**不适合每天用**。

### 方案 D：Home Assistant + Xiaomi Miot（选它）

**优点**：

- Xiaomi Miot 集成**自己维护登录**，跟着小米接口变，不依赖那个死掉的库
- 设备抽象成「实体」，灯就是 `light.xxx`，空调就是 `climate.xxx`，协议细节被吃掉
- 加设备、换设备不用改插件

**缺点**：多一个容器、1.5 GB 镜像、配置十分钟。

**结论**：**把复杂度前置到一次性安装，换取长期稳定。** 这是一次性成本 vs 每天成本的选择。

## 三、为什么插件只做「转发」，不做「集成」

插件里没有一行小米协议代码，只有：

```
HTTP 请求 → HA REST API → 返回 JSON
```

原因是**职责分离**：

| 谁 | 负责什么 |
|---|---|
| HA + Xiaomi Miot | 跟小米打交道（登录、协议、设备型号适配） |
| 本插件 | 把 HA 的能力翻译成 AI 能用的工具 |

好处：

- 小米改接口 → 上游社区修，插件不用动
- 用户加新设备 → 在 HA 里点两下，插件自动能控
- 插件代码小（两个文件），好读好改

代价：多一层依赖。但如果 HA 挂了，直连方案大概率也挂（同一个云）。

## 四、数据流

### 一次「关灯」发生了什么

```
1. 用户：「把卧室灯关了」
2. 模型选择工具：ha_control { entity: "卧室灯", action: "off" }
3. 插件：读 ~/.dsh/homeassistant/config.json 拿 url + token
4. 插件：resolveEntity("卧室灯")
     → aliases 命中？→ 是，light.yeelink_mbulb3_92ae_light
5. 插件：POST http://localhost:8123/api/services/light/turn_off
     Body: { "entity_id": "light.yeelink_mbulb3_92ae_light" }
     Header: Authorization: Bearer eyJ...
6. HA：找 Xiaomi Miot，走云端/局域网把灯关了
7. HA：返回 []（成功）
8. 插件：{ ok: true, entity: "light...", action: "off" }
9. 模型：「关了。」
```

### 实体名解析顺序

1. `config.aliases` 精确匹配
2. 完整实体 id
3. 实体的 `friendly_name` 包含关键词
4. 实体 id 包含关键词

**为什么要有这一步**：模型不该被迫记住 `light.yeelink_mbulb3_92ae_light` 这种串。
中文口语名更稳定，也更符合用户说话的习惯。

## 五、配置为什么不用 DSH 的 settings store

DSH 插件通常导出 `Config`（schemastery schema），设置页自动渲染。

本项目没走这条路，原因：

1. **前端要「改完立刻生效」**：设置页直接 POST 到 `/api/ha/config`，写文件，下一次工具调用就读到新值。走 settings store 需要等宿主同步。
2. **令牌是敏感字段**：放自己的 JSON 文件里，路径明确、好删、不进统一配置导出。
3. **配置形状会变**（以后要加 `aliases`、场景列表等），自己管更自由。

代价：设置页要自己写（就是 `client.js` 那 300 行）。

## 六、安全模型

| 资产 | 存哪 | 谁能读 |
|---|---|---|
| HA 长期令牌 | `~/.dsh/homeassistant/config.json` | 本机当前用户 |
| HA 本身 | `localhost:8123` | 本机 |
| 小米账号密码 | **插件不存**，只存在 HA 的配置里 | HA 自己 |

设计原则：

- **插件不碰小米账号**，只跟 HA 说话
- **令牌只存本机**，不上传、不打日志
- **HA 不暴露公网**，默认只监听本机

风险提示：令牌有效期很长（默认十年），泄露等于把家门钥匙拍照发出去。
建议定期在 HA 里删掉重建。

## 七、失败模式与降级

| 失败点 | 表现 | 降级方案 |
|---|---|---|
| Docker 没起 | `docker info` 报错 | 手动启动 Docker Desktop |
| HA 没起 | 连接 `ECONNREFUSED` | `docker start homeassistant` |
| 集成没加载 | 实体数量为 0 | 检查目录 + 重启容器 |
| 小米账号掉线 | 实体 `unavailable` | HA 里重新加载集成 |
| 令牌失效 | 401 | 重建令牌 |
| 设备离线 | 请求超时 | 换设备 / 等它上线 |

**没有「静默失败」**：所有工具都返回 `{ ok: false, error }`，模型能看到原因，
不会假装成功。

## 八、扩展点

想加功能，从这两处下手：

1. **加工具**：在 `index.js` 的 `apply()` 里 `tool({...})`，照着 `ha_control` 抄
2. **加前端**：在 `client.js` 的 `Panel` 里加一块 UI，后端在 `handle()` 里加一条路由

已经想好的方向见 README 的「路线图」。

## 九、写这个项目踩过的坑（给后来人）

1. **别用 `fetch` 打 `localhost`**：Node 的 fetch 在某些环境会对本地地址做额外处理，本项目统一用 `http.request`。
2. **`apply` 必须是同步函数**：写成 `async` 时，某些 cordis 版本不会 await，导致工具一个都注册不上。
3. **`dsh.client.inject` 写错 = 设置页不出现**：要跟能正常显示的插件保持三件套一致。
4. **前端别直接调 HA**：会有 CORS 和令牌暴露问题，统一走后端的 `/api/ha/*`。
5. **`ghcr.io` 在国内拉不动**：准备好镜像站备用清单。
